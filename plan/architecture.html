Architecture board

A knowledge system for Requirements, Test Cases and Risk Items. Users ask questions in plain English; agents answer only from the database and can only propose changes that a human confirms.

01

Product structure

Five screens, each answering one user question.

Chat

“Which requirements have no test cases?” Answer plus the evidence records and tool trace.

Browse

Requirements, test cases and risks with filters such as high risk.

Pending changes

A proposed update shown as a diff. Confirm or reject.

Impact report

After a change: which tests and risks are affected.

Audit log

Append-only history of every modification.

02

System architecture

Layers depend inward. Agents never touch the database: they go through services, which enforce every rule.

Rule of the architecture: the LLM chooses a tool and fills its arguments; code executes it. Even a fully misled model can only call read tools or propose a change.

06

Write flow and impact workflow

Nothing changes until a human confirms. Applying a change triggers the automated impact analysis in the same transaction.

  1. 1
    Propose

    Agent or user creates a pending change with base_version and a diff preview. Nothing is applied.

  2. 2
    Confirm

    One transaction: version must still match (else 409), rules validated, change applied, version bumped.

  3. 3
    Impact analysis

    Find linked test cases (pass → not_run) and risks (flag for review). Save the report.

  4. 4
    Audit entry

    Old and new values, actor, source and request id, committed with the change.

  5. 5
    Summary

    After commit, the LLM phrases the report in three sentences. It never decides the impact.

Why this design

Human in the loop. The agent has no apply tool, so a wrong guess costs a rejected proposal, not corrupted data.
Atomic. Change, impact and audit commit together or not at all.
Idempotent. Confirming the same change twice does nothing the second time.
Example: Changing REQ-009 (metering accuracy) resets its 4 test cases to not_run and flags RISK-003 (inaccurate billing) for review.
07

Rules and validations

The same rule is checked in more than one layer, so one mistake never corrupts data.

LayerRules enforced
DatabaseUnique primary keys · foreign keys · CHECK on enums and 1-5 ranges · NOT NULL · append-only audit triggers
DomainID formats REQ-### TC-### RISK-### · status state machine (obsolete is final) · risk score and level
ServiceReferenced records must exist · version must match · idempotent confirm · audit in the same transaction · rollback on failure
AgentRead or propose only · grounding check · loop and token caps · confirmation required to apply
Seed pipelineEvery generated row validated by the same rules · bad rows reported and skipped
